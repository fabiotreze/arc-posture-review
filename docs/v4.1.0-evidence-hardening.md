# v4.1.0 evidence hardening

## Scope

This change is limited to evidence interpretation for `CHK-42`, `CHK-55`, `CHK-57`, and `CHK-63`, negative regression tests, and idempotent GitHub Release publication. It does not add checks, scenarios, customer evidence, or customer reports.

## Preserved contracts

- Exactly 64 controls: `CHK-01` through `CHK-64`.
- Exactly 11 security scenarios: `AS01` through `AS11`.
- Canonical assessment contract: `assessment-result.v4`, contract version `4.0.0`.
- Collector input schema remains version 3.
- Control Result and Evidence Coverage remain independent axes.

## Normative evidence rules

### CHK-42 — Patch assessment

- `PASS` requires exactly one successful assessment row per connected machine.
- The row must have a parseable timestamp and parseable, non-negative critical/security counts.
- Patch authority must be `AutomaticByPlatform`; an external authority requires documentary evidence and is not inferred.
- Missing, duplicate, unsuccessful, malformed, or untimestamped evidence yields `PARTIAL` unless explicit negative evidence exists.
- A failed patch extension or explicit pending critical/security count remains `FAIL`; simultaneous evidence gaps set coverage to `PARTIAL` instead of masking the failure.

### CHK-55 — OS security baseline

- Only bounded, recognized OS security baseline assignment names qualify; a generic name containing `baseline` is insufficient.
- `PASS` requires every connected machine to have recognized, `Compliant`, timestamped evidence.
- Explicit `NonCompliant` evidence or no recognized assignment from a complete Machine Configuration query is `FAIL`.
- Pending, missing, conflicting, generic-name, or untimestamped compliance evidence yields `PARTIAL` unless an explicit failure is also present.

### CHK-57 — Antivirus and EDR health

- High/Medium/Critical unhealthy endpoint-protection recommendations are conclusive `FAIL` evidence.
- Lower-severity unhealthy recommendations are `WARN`.
- A missing or non-`Succeeded` MDE extension is a coverage proxy, not proof that the sensor is absent or unhealthy; by itself it yields `PARTIAL`.
- Explicit negative Defender evidence takes precedence over the proxy gap; coverage remains `PARTIAL` when both occur.

### CHK-63 — Defender for Servers per Arc machine

- The subscription plan is not substituted for an unread resource-level effective plan.
- An explicitly read effective `Free` plan is `FAIL`.
- An explicitly read difference or override is `WARN`.
- An unread resource plan or unread subscription comparison is `PARTIAL`, never `PASS` and never inferred as `Free`.
- When explicit failure/warning and unread machines coexist, retain the conclusive result with `PARTIAL` coverage.

## Release workflow idempotency

The release workflow performs an upsert:

1. If the release does not exist, create it with the generated notes and collector asset.
2. If it exists, update title/notes and upload the collector asset with `--clobber`.

A rerun for an existing tag therefore does not fail with `a release with the same tag name already exists`.

## Negative regression coverage

`tools/Test-EvidenceHardening.py` and `tests/fixtures/evidence-hardening-negative.v4.1.0.json` cover missing timestamps, duplicate rows, explicit failure plus incomplete coverage, failed MDE proxy evidence, unread resource plans, and precedence of conclusive negative evidence.
